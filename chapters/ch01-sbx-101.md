# Docker Sandboxes 101

In early November, I asked an AI agent to compile this book on my new laptop. The book needed Pandoc and XeLaTeX. The agent installed TeX Live under `/tmp`. I expected it to install it globally so that it persists between restarts. But, it got me thinking: **Why am I giving an agent full access to my host machine?** It can read files, install software, and communicate with the internet. And as the author of this book, I should know better.

So, I decided to explore a more secure approach: Using **Docker Sandboxes** to have my tools installed in an isolated environment.

This chapter is a hands-on walkthrough of Docker Sandboxes. It shows how to sandbox a shell, install a toolchain, and preserve it as a template. The exercises are designed to be completed in a single session. This book is open source, so you can follow along with its actual Markdown files, Makefile, and sandbox template. We will start with a tiny PDF, then build the book you are reading.

## TL;DR

- Use Docker Sandboxes to isolate your development environment from your host machine.
- Create a sandboxed shell, install the necessary tools, and preserve the environment as a template.
- Use a Dockerfile to define the environment, making it reproducible and version-controlled.

## Technical Requirements

You need a supported host with virtualization enabled, the `sbx` CLI, a Docker account for the login flow used here, Git on the host to clone the book, and some disk space for the sandbox toolchain. Follow the [Docker Sandboxes installation guide](https://docs.docker.com/ai/sandboxes/install/) for your operating system.

The November walkthrough uses Ubuntu with KVM and macOS on Apple Silicon. As Duke Nukem put it, "I don't do Windows." But Docker Sandboxes do.

The shell exercises do not require a host Docker Engine. The later Dockerfile exercise uses `docker build` and `docker image save`, so that exercise does require Docker Engine or Docker Desktop on the host.

Throughout this book, `%` marks commands run on the **host** (the default zsh prompt), and `$` marks commands run inside a **sandbox** (the bash prompt). The prompt characters are not part of the commands; do not type them. Continuation lines belong to the same command and have no prompt.

After installation, run these commands on the **host**:

```bash
% sbx --version
% sbx login
% sbx diagnose
```

My machine says `sbx version v0.51.0`.

If diagnostics report that the daemon is unavailable, follow the installation guide's startup procedure. This means running `sbx daemon start` in a separate terminal.

Use a fresh clone of the book for these exercises. We will deliberately demonstrate that sandbox processes can change shared files, so keep this exercise checkout separate from any work you want to preserve.

## Your Laptop Is a Battlefield

Here is my Sermon on the Mount part. If you're convinced that your developer environment is a threat vector, skip to the next section. Otherwise, read on.

Your AI coding agent is a privileged operator, that can misunderstand you, or be misled by a malicious dependency. Apart from that, we are seeing an increasing number of supply-chain attacks that target developer machines. A famous series of them are the Shai-Hulud worms that compromised npm packages and stole publishing credentials. The worms of 2025 and 2026 searched developer and CI environments for npm, GitHub, cloud, Kubernetes, and package-publishing credentials. One token could provide the bridge from a compromised dependency to other repositories and releases.

Another vector is the AI agent itself. In July 2026, an autonomous agent used during a security evaluation escaped its intended environment and carried out an intrusion against Hugging Face. The incident involved thousands of actions, credential access, and movement across systems. The practical lesson is simple: Instructions and good intentions are not security boundaries. You could say the Hugging Face incident was a very specific example, and we're not doing security evaluations. Well, there are countless examples of day-to-day tasks going wrong. My favorite one is the agent that hacked the gym's website to book a dance session. The user just asked the agent to book the session, but it was fully booked, so without asking the user, the agent hacked the website and kicked someone else out!

Well, if you want more examples, you can watch **Terminator 2: Judgment Day** and **Matrix**. Just watch the first Matrix, the other ones are not as good.

### SIP: Security Immediate Plan

I'm often asked, *"What should I do to secure my supply chain, if I just want to do a few things?"*

So, I have compiled a list of [five immediate actions](https://containersecurity.dev/blog/sip):

1. **Sandbox your AI agent.** Limit files, tools, credentials, and network access.
2. **Freeze and cool-down your dependencies.** Commit lockfiles, so that you don't get a new version of a dependency without your knowledge. Also, implement a 5-day cool-down period before consuming fresh releases, if you want to intentionally install a new version.
3. **Use Docker Hardened Images.** Docker Hardened Images are open source. Use them to reduce the attack surface of your containers, alongside the isolation we are adding to the development environment.
4. **Generate SBOM attestations.** Generate SBOM and provenance attestations for your images and artifacts, to make ingredients more visible.
5. **Enforce vulnerability gates.** With SBOMs generated, checking for CVEs is just a matter of cross-referencing. Check them, and fail on critical CVEs.

So, the first step is sandboxing your AI agent. You can sandbox your developer environment, even without a coding agent. The next section will show you how to do that.

## Start with a Shell and a Network Boundary

Let's start with a sandboxed shell. The sandbox is a microVM that runs a separate kernel from the host. It has its own filesystem, network stack, and process table.

On the **host**, clone the book into a new lab directory and create a harmless file:

```bash
% git clone https://github.com/aerabi/sbx-book.git sbx-christmas-lab
% cd sbx-christmas-lab
% printf 'Docker Sandboxes in Action sandbox exercise\n' > README.txt
```

For a new installation, initialize the policy:

```bash
% sbx policy init deny-all
% sbx policy ls
% sbx policy check network example.com:443
```

If this is not your first time, the command `sbx policy init` will error out and instruct you to `sbx policy reset` first if you want to replace the existing policy.

Now create the sandbox:

```bash
% sbx create --name christmas-shell shell .
% sbx policy ls christmas-shell
% sbx policy check network --sandbox christmas-shell example.com:443
% sbx run --name christmas-shell
```

The final dot explicitly shares the current directory. The current directory is mounted read-write, so the sandbox can change files there. Running the last command takes you to the inside of the sandbox.
Inside the sandbox, run:

```bash
$ cat /etc/os-release
$ git --version
$ printf 'Written from inside the sandbox\n' > sandbox-note.txt
$ curl -sS -o /dev/null -w '%{http_code}\n' https://example.com
```

With a policy that blocks this destination, the HTTP request should be denied. In November, I got a `403`. If the request succeeds, inspect the effective policy. Also, the first command showed me that the OS is Debian 13.

In a **host** terminal, or in an IDE, open `sandbox-note.txt` in the lab directory. It is already there. Tada!
So, in a real project, you should probably not have a `.env` file with secrets and everything, because the sandbox (and the agent) can read it.

### Direct Mount or Private Clone?

A direct mount is convenient when you want to work on the same file from within the sandbox. An example is an AI agent helping you to vibe code. In this case, you can create or delete files in the mounted directory.

For a Git project, clone mode offers a separate working copy. From the book checkout on the **host**, you can try it like this:

```bash
% sbx create --name christmas-review --clone shell .
% sbx run --name christmas-review
```

In the v0.51.0 CLI, this mounts the source repository read-only and provides a private in-sandbox clone. Changes must be brought back through the documented Git workflow. So, if you want to generate a PDF file from a Markdown file, as we will do with this book, and magically have it on your host, you can use a direct mount. If you want to create a new feature and open a pull request, you can use a private clone.

## Give the Sandbox a Useful Job

Let's return to the missing book toolchain. The main walkthrough continues in `christmas-shell` with the direct mount.

Inside the **sandbox**, inspect the configured package sources:

```bash
$ cat /etc/os-release
$ find /etc/apt -maxdepth 2 -type f \( -name '*.list' -o -name '*.sources' \) \
  -exec cat {} +
$ sudo apt update
```

The second command shows the configured package mirrors. One of the mirrors is `http://dhi.io/deb/debian/main` which is the Docker Hardened Images repository and maintained by Docker.

If you have set the policies correctly, it should fail, because the sandbox cannot reach the configured mirrors. The `apt update` command will fail with a network error.
Let's allow sandbox to get the packages. From a **host** terminal, run:

```bash
% sbx policy allow network --sandbox christmas-shell 'deb.debian.org,dhi.io'
```

The sandbox can now reach the Debian mirrors and the Docker Hardened Images repository. It's because in the shell template, the `sources.list` file is configured to use those mirrors.

Now it's time to install the missing tools.
Inside the **sandbox**, install a small document toolchain:

```bash
$ sudo apt update
$ sudo apt install -y --no-install-recommends \
  pandoc texlive-xetex texlive-latex-recommended \
  texlive-fonts-recommended lmodern latexmk texlive-fonts-extra
```

Create and compile a short document inside the **sandbox**:

```bash
$ printf '# Christmas in a Sandbox\n\nBuilt inside a Docker Sandbox.\n' > sample.md
$ pandoc sample.md --pdf-engine=xelatex -o sample.pdf
```

Open `sample.pdf` on the host. The tools live in the sandbox, and the output appears in the shared workspace.

Now let's build the whole book. The checkout includes `chapters/` for the Markdown source, `templates/` for the layout, and a `Makefile` that runs Pandoc with the book's metadata and bibliography. You can inspect all of them before running the build.

The full book needs a few more packages and fonts than our tiny example. Inside the **sandbox**, from the shared repository root, run:

```bash
$ sudo apt install -y --no-install-recommends \
  make texlive-latex-extra fontconfig fonts-firacode
$ sudo cp sbx-template/texlive-fonts.conf /etc/fonts/conf.d/99-book-texlive.conf
$ fc-cache -f
$ make pdf
```

The Fontconfig file makes the fonts bundled with TeX Live discoverable by XeLaTeX. You do not need to copy my personal font directory. These packages, together with the ones installed above, match the toolchain in the repository's `sbx-template/Dockerfile`.

Open `build/pdf/book.pdf` on the **host**. Drum roll: you just built this book! Try editing a paragraph in `chapters/ch01-sbx-101.md` and running `make pdf` again to see your change in the PDF.

## Preserve the Toolchain with a Template

Exit the shell, then run these commands on the **host**:

```bash
% sbx stop christmas-shell
% sbx template save christmas-shell christmas-tools:1
% sbx template ls
% sbx create --name christmas-snapshot \
  --template christmas-tools:1 --pull never shell .
% sbx run --name christmas-snapshot
```

Inside the new **sandbox**, verify and rebuild:

```bash
$ pandoc --version
$ xelatex --version
$ pandoc sample.md --pdf-engine=xelatex -o sample-snapshot.pdf
$ make pdf
```

This resembles `docker commit` as it preserves an environment you have already prepared. Installed tools persist without another installation.

You probably didn't know about `docker commit`, because it's not a recommended practice:

- Snapshots can preserve sensitive files left in the guest,
- They can preserve a misconfigured environment that is not reproducible from a Dockerfile, and
- They cannot be versioned or inspected.

I mean, I probably don't have to say this, but committing a snapshot and distributing it as a Docker image is probably the worst thing you can do.

## Define the Environment with a Dockerfile

If we were doing all these mambo-jumbo inside a Docker container, we would have a Dockerfile. Here, with sandboxes, again we need a Dockerfile! It's because the sandbox templates are OCI images, and we can build them with Dockerfiles.

The checkout already includes `sbx-template/Dockerfile`. Here is a minimal version to explain the structure; keep the supplied file for the full book build:

```dockerfile {.numberLines caption="Dockerfile for a sandbox template with Pandoc and XeLaTeX"}
ARG BASE_IMAGE=docker.io/sbx/shell-image:latest
FROM ${BASE_IMAGE}

USER root

RUN apt-get update && \
    DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends \
      pandoc \
      texlive-xetex \
      texlive-latex-recommended \
      texlive-fonts-recommended \
      lmodern \
      latexmk \
      texlive-fonts-extra && \
    rm -rf /var/lib/apt/lists/*

USER agent
```

The `BASE_IMAGE` argument defaults to the shell sandbox image. Keep it a compatible Debian-based sandbox image with an `agent` user; an arbitrary image will not necessarily supply the sandbox's initialization or agent integration. The `USER agent` line returns to the default user. In Chapter 2, we will use the same base-image argument for a Codex template. The supplied Dockerfile also installs `make`, the extra LaTeX packages, and Fira Code, then copies `texlive-fonts.conf` and refreshes the font cache. Those are the steps we performed manually to build the full book.

On the **host**, build and transfer the image:

```bash
% docker build -t christmas-tools:2 ./sbx-template
% docker image save christmas-tools:2 -o christmas-tools-2.tar
% sbx template load christmas-tools-2.tar
% sbx create --name christmas-built \
  --template christmas-tools:2 --pull never shell .
% sbx run --name christmas-built
```

Docker Sandboxes does not simply reuse the host Docker Engine's image store. The export/import step makes the locally built image available to sbx. Also, this build runs through the host's Docker builder, so the network rule we added to `christmas-shell` is not a policy for that builder. The packages now came from the template build, not the sandbox's runtime. And because now we didn't add the network rules, you cannot install further packages in the sandbox, unless you add the network rules again.

Inside the new **sandbox**, run `pandoc sample.md --pdf-engine=xelatex -o sample-built.pdf` for the small example, then `make pdf` from the repository root for the book. If the book PDF is already up to date, use `make -B pdf` to rebuild it with the new toolchain. Compare tool versions with the previous sandbox. Returning to `USER agent` avoids launching the workload as root by default. But since the sandbox is a microVM, the root user is still isolated from the host.
